# t-3-3 — 3.3 Релизные стратегии: релизные поезда, continuous delivery, feature flags, canary, blue-green, dark launch, rollback-планы

3.3 Релизные стратегии: релизные поезда, continuous delivery, feature flags, canary, blue-green, dark launch, rollback-планы
Теория
Релизная стратегия отвечает на два разных вопроса, которые часто смешивают: когда и как часто изменения попадают в прод (ритм поставки) и как именно изменение доходит до пользователей (техника раскатки). Разделение этих вопросов — первое, что показывает зрелость кандидата. Ритм: релиз по готовности (когда фича готова — выкатываем), релизный поезд (release train — фиксированное расписание, например каждые две недели или каждый вторник; кто успел — едет, кто не успел — ждёт следующего), continuous delivery (CD — каждое изменение, прошедшее пайплайн, готово к выкатке в любой момент; выкатка — решение бизнеса), continuous deployment (каждое изменение автоматически попадает в прод). Техники раскатки: canary, blue-green, feature flags, dark launch и их комбинации.
Релизный поезд решает проблему координации: когда 10+ команд поставляют в один продукт (мобильное приложение, монолит), релиз по готовности каждой команды означает хаос. Поезд даёт предсказуемость: все знают дату, code freeze (заморозку кода) перед ней, порядок регресса. Цена — фичи ждут поезда, и в двухнедельном ритме средняя задержка — неделя. Правило поезда: расписание не двигается ради фичи; фича не готова — едет на следующем. Как только это правило нарушается «ради важной фичи», поезд перестаёт работать. Continuous delivery снимает задержку, но требует инфраструктуры: автоматические гейты, изолированные развёртывания, feature flags и быстрый откат. В компаниях уровня Яндекса типичны оба подхода: поезда для мобильных приложений (там ритм диктуют сторы), CD для бэкенд-сервисов.
Техники раскатки:
Canary (канареечный релиз) — новая версия выкатывается на малую долю трафика или пользователей (1%, затем 10%, 50%, 100%) с контролем метрик на каждом шаге. Дефект затрагивает малую долю; откат — переключение трафика назад. Требует маршрутизации трафика и метрик, сравнимых между версиями.
Blue-green — две идентичные среды: текущая (blue) и новая (green). Трафик переключается целиком с одной на другую; откат — обратное переключение за секунды. Требует удвоенной инфраструктуры на время релиза и осторожности с миграциями БД (схема должна быть совместима с обеими версиями).
Feature flags (feature toggles, флаги функций) — код новой функции есть в проде, но включается конфигурацией: для всех, для процента, для сегмента (сотрудники, бета-пользователи). Разделяет deploy (выкатку кода) и release (включение для пользователей). Позволяет откатить функцию без новой выкатки — критично для мобильных приложений, где новая сборка через сторы занимает дни. Цена — сложность кода и обязательная гигиена: флаги удаляются после полной раскатки, иначе через год их 400.
Dark launch (тёмный запуск) — новая функция работает в проде на реальном трафике, но её результат не показывается пользователям: например, новый поисковый движок обрабатывает те же запросы параллельно, результаты сравниваются и логируются. Проверяет производительность и корректность под настоящей нагрузкой без риска для пользователей. Цена — двойная нагрузка и инфраструктура сравнения.

Rollback-план (план отката) — обязательная часть релиза, и его отсутствие в чек-листе — красный флаг. Хороший план отвечает: что является триггером отката (метрика и порог — ошибки выше [X%], латентность p99 выше [Y] мс, жалобы в поддержку выше [N] за час), кто принимает решение (дежурный, без согласования — при ясных порогах), как технически откатываем (переключение трафика, выключение флага, предыдущая сборка), сколько это займёт, что с данными (главная сложность: если новая версия записала данные в новом формате, откат кода не откатит данные — нужна обратно совместимая схема или миграция вперёд с флагом), что с пользователями на клиентах, которые нельзя откатить (мобильные приложения — см. 3.4). Приём «roll forward» — вместо отката быстро выкатить исправление — допустим, только если он реально быстрее и надёжнее отката, что редко для критичных систем.
Заметка. Техники комбинируются: типичный современный релиз бэкенд-сервиса — CD с canary-раскаткой, где новая функция дополнительно скрыта за feature flag, а включение флага идёт по сегментам. Мобильный релиз — поезд с поэтапной раскаткой через сторы плюс серверные флаги для функций. Умение собрать комбинацию под контекст — признак Senior.
Для банковского контекста релизные стратегии сталкиваются с ограничениями: релизные окна (ночь, выходные) для критичных систем, требование согласования изменений, монолит без возможности частичной раскатки. Кандидат, который вводил поезда и флаги в такой среде, может показать, как двигался от «релиз раз в месяц в ночь с субботы» к «поезд раз в две недели плюс флаги для включения в рабочее время» — с описанием того, что для этого пришлось изменить в архитектуре и в договорённостях с ИБ.
Что проверяет интервьюер
JuniorЗнает, что такое релизный поезд и feature flag, различает выкатку кода и включение функции, может объяснить, зачем нужен план отката. Проверяют, понимает ли кандидат правило поезда («не двигаем расписание ради фичи») и знает ли, как релизится его команда и что происходит при провале релиза.
Middle / DMОрганизует релизный процесс для 2–5 команд: выбирает ритм, ведёт релизный чек-лист, пишет план отката с триггерами, использует флаги для развязки команд. Проверяют на кейсе: команда просит сдвинуть поезд ради фичи — что делать; релиз упал — как откатывать, если данные уже записаны. Ожидается опыт хотя бы одного отката с разбором.
Senior / Lead TPMПроектирует релизную стратегию для направления: комбинация техник под разные типы систем, переход от поездов к CD, работа с миграциями БД при blue-green, гигиена флагов. Проверяют глубину: почему canary не поймает дефект в редком сценарии, что делать с состоянием при переключении blue-green, как построить dark launch для замены скоринга. Ожидается понимание архитектурных предпосылок каждой техники.
HeadОтвечает за релизную политику организации: какие системы на каком ритме, какие инвестиции в платформу раскатки, как политика отката закреплена, как релизные риски отчитываются. Проверяют, как кандидат обосновывает переход с ежемесячных релизов на еженедельные перед правлением и ИБ, и как измеряет эффект.
Примеры ответов
Вопрос: Как вы выбираете стратегию раскатки для конкретного изменения? Приведите пример, когда выбрали одну технику и отказались от другой.
Слабый ответ
Мы стараемся использовать canary для всех релизов — сначала 10%, потом 100%. Это безопасно и позволяет откатиться, если что-то пошло не так. Для больших изменений делаем blue-green, чтобы было две среды. Feature flags тоже используем для новых фич, чтобы включать постепенно. Пример: при релизе нового экрана переводов сделали canary на 10% пользователей, посмотрели метрики день, потом раскатили на всех. Проблем не было. Главное — всегда иметь возможность откатиться и следить за мониторингом.
Сильный ответ
Выбор идёт от трёх вопросов: как быстро дефект проявится на метриках, можно ли раскатывать частично, что с данными при откате. Пример — замена движка расчёта комиссий в монолите. Canary отклонил: расчёт комиссий детерминирован, дефект проявится не в ошибках, а в неверных суммах у части клиентов, и на 1% трафика мы бы неделю не заметили ошибку в редком тарифе. Blue-green не подходил: переключение 100% сразу для финансовой логики — неприемлемый риск. Выбрали dark launch: новый движок [срок] считал комиссии параллельно со старым на всём трафике, результат логировался и сравнивался, пользователь видел старый. Расхождения — около [X%] в первую неделю, все разобраны, три из них — ошибки в старом движке. Когда расхождения были нулевыми [N] дней подряд (это был гейт), переключили через флаг по сегментам: сотрудники, [X%] клиентов, все. Откат — выключение флага, старый движок оставался живым ещё квартал. Цена — двойная нагрузка на базу тарифов, которую пришлось масштабировать на время.
Разбор: Слабый ответ применяет canary «для всего» без понимания его ограничений, описывает техники как список, а пример не содержит выбора — «сделали canary, проблем не было» ничего не говорит о мышлении. Сильный ответ начинает с критериев выбора, показывает, почему две популярные техники не подходят для конкретного изменения (детерминированная логика, редкие сценарии, финансовый риск), выбирает dark launch с гейтом на переключение, комбинирует с флагом и сегментами, называет цену. Интервьюер видит инженерное понимание, а не словарь.
Кейсы
Кейс 1. Сдвинуть поезд ради фичи
Релизный поезд интернет-банка выходит каждый второй вторник. В пятницу перед code freeze продакт кредитного направления просит сдвинуть поезд на три дня: фича «предодобренный кредит на главной» почти готова, а маркетинг уже запланировал рассылку на среду после релиза. В поезде — фичи ещё шести команд, включая исправление дефекта, из-за которого часть клиентов не видит выписку. Что вы делаете?
Подсказки
Что происходит с поездом как институтом, если его сдвинуть один раз?
Кто ещё пострадает от сдвига и знают ли они об этом?
Какие варианты дать продакту, кроме «нет»?
Что нужно было сделать за три недели до этого?
Развёрнутый разбор
Правило поезда — расписание не двигается. Сдвиг на три дня ради одной фичи означает: шесть команд получают задержку, исправление дефекта с выпиской ждёт (это прямой ущерб клиентам), и главное — следующий продакт придёт с той же просьбой, потому что прецедент создан. Поезд, который двигается, — не поезд. Но прямое «нет» продакту, у которого маркетинг с рассылкой, — не решение, а конфликт.
Варианты для продакта. Первый: фича едет в этот поезд за feature flag в том состоянии, в котором успела к freeze, доделывается в течение следующей недели и включается флагом, когда готова — маркетинг сдвигает рассылку на день включения, а не на дату поезда. Это работает, если незавершённая часть не ломает остальное и скрыта флагом. Второй: фича едет следующим поездом через две недели, маркетинг переносит рассылку — честно, но продакт теряет две недели. Третий: внеочередной релиз только этой фичи в четверг после поезда — возможен, если пайплайн позволяет независимый релиз и фича не трогает общие компоненты; цена — дополнительный регресс и нагрузка на релизную команду.
Развилка между первым и третьим. Первый лучше, если архитектура поддерживает флаги и фича изолирована — это стандартный путь, который не создаёт прецедента. Третий — если флагов нет (монолит без инфраструктуры флагов), и тогда это повод для отдельного разговора о её внедрении. Что нужно было раньше: продакт должен знать расписание поездов на квартал вперёд и планировать маркетинг от даты поезда плюс запас, а не от оптимистичной готовности фичи. Это правило коммуникации, которое вы вводите: расписание поездов публикуется, маркетинговые даты привязываются к поезду N+1, а не N. Интервьюер ждёт, что вы защитите поезд и одновременно дадите продакту путь.
Кейс 2. Откат, который не откатывает данные
Сервис истории операций выкатили blue-green с новой версией, которая пишет операции в новую таблицу с расширенной схемой. Через 40 минут на 100% трафика — рост ошибок в мобильном приложении: старые версии приложения не парсят новое поле. Дежурный переключает трафик на blue. Ошибки в приложении исчезают, но операции, записанные за 40 минут в новую таблицу, не видны пользователям — старая версия читает старую таблицу. Поддержка получает жалобы «пропали переводы». Как вы действуете сейчас и что должно было быть в плане релиза?
Подсказки
Почему blue-green не откатил данные и какое правило проектирования схемы нарушено?
Что делать с 40 минутами данных: миграция назад, чтение из двух таблиц, roll forward?
Какая ошибка совместимости с клиентами допущена и как её ловят гейтом?
Что нужно записать в постмортем как системное изменение?
Развёрнутый разбор
Две ошибки в одном релизе. Первая: нарушен принцип совместимости схемы данных с обеими версиями кода (expand-contract: сначала расширяем схему так, чтобы старый код продолжал работать, выкатываем новый код, пишущий в оба места или в совместимый формат, и только потом сужаем). Новая версия писала в новую таблицу, старая её не знала — откат кода стал невозможен без потери данных. Вторая: нарушена обратная совместимость API с клиентами — новое поле в ответе сломало старые версии мобильного приложения, что значит, клиенты парсят ответ строго, а контрактные тесты на старые версии клиентов не было в гейтах.
Сейчас — инцидент с приоритетом «данные клиентов не видны». Развилка. Вариант А: срочная миграция 40 минут операций из новой таблицы в старую скриптом (обычно час работы разработчика плюс проверка) — пользователи видят операции через час-два, состояние системы возвращается к известному (blue). Риск — ошибка в скрипте миграции под давлением. Вариант Б: roll forward — быстро исправить в green ответ API так, чтобы новое поле не отдавалось старым версиям клиентов (по заголовку версии), и переключить трафик обратно на green; данные из новой таблицы сразу видны. Риск — вы снова на новой версии, в которой мог быть не один дефект, без прохождения гейтов. Выбирайте А, если исправление green требует больше 30 минут или не полностью понятна причина; Б — если причина локализована точно, исправление тривиально и есть возможность прогнать хотя бы smoke-тесты. При финансовых данных обычно выбирают А: вернуться к известному состоянию надёжнее.
Постмортем — системные изменения, не «быть внимательнее»: правило expand-contract для всех миграций схемы как обязательный пункт архитектурного ревью; контрактные тесты против [N] последних версий мобильного приложения в гейте перед релизом; blue-green только для изменений без миграции схемы, иначе canary с двойной записью; в плане отката — явный раздел «данные, записанные новой версией: как становятся видимыми после отката». Это то, что интервьюер хочет услышать: не героизм дежурного, а изменение системы, чтобы такой класс инцидентов стал невозможным.
Кейс 3. От ежемесячных ночных релизов к еженедельным
Монолит розничного банка релизится раз в месяц, в ночь с субботы на воскресенье, с окном простоя 4 часа и 30–40 участниками релиза. Каждый релиз — 200+ изменений от 20 команд, 1 из 3 релизов требует отката или срочного хотфикса. Руководство хочет еженедельные релизы без простоя за год. ИБ и служба эксплуатации против: «больше релизов — больше рисков». Как вы построите переход и что скажете противникам?
Подсказки
Почему «больше релизов — больше рисков» неверно и как это показать данными?
Какие архитектурные и инфраструктурные предпосылки нужны для релиза без простоя?
В какой последовательности менять ритм: сразу еженедельно или ступенями?
Какие метрики покажут эксплуатации и ИБ, что риск снизился?
Развёрнутый разбор
Аргумент против «больше релизов — больше рисков»: риск релиза пропорционален размеру изменения, а не числу релизов. Релиз из 200 изменений — это 200 потенциальных причин отката и невозможность найти виновника за ночь; релиз из 50 изменений — вчетверо меньше поверхность, и откат касается четверти работы. Данные DORA (см. 3.6) показывают, что команды с частыми релизами имеют меньшую долю неудачных изменений, а не большую. Для эксплуатации и ИБ это надо показать на своих данных: доля откатов и среднее время восстановления за последний год по размеру релиза.
Предпосылки, без которых еженедельный релиз невозможен: автоматизированный регресс критичных сценариев (сейчас, вероятно, ручной регресс занимает неделю — при еженедельном ритме он не влезает), обратно совместимые миграции схемы (expand-contract) для релиза без простоя, feature flags для развязки готовности фич и даты релиза, blue-green или rolling deployment для монолита (требует, чтобы две версии могли работать параллельно), релизный чек-лист с автоматизированными пунктами вместо 40 человек в ночи.
План по ступеням: квартал 1 — автоматизация регресса критичных сценариев и внедрение флагов, релиз остаётся ежемесячным, но окно простоя сокращается за счёт совместимых миграций; квартал 2 — раз в две недели, ночью, с сокращённым составом участников, измерение доли откатов; квартал 3 — раз в две недели, но в рабочее время в непиковые часы с blue-green без простоя для части модулей; квартал 4 — еженедельно. Каждая ступень — с гейтом: доля откатов не выше предыдущего уровня, иначе не переходим.
Развилка. Вариант А: переход ступенями по всему монолиту, как описано — предсказуемо, но год работы всех 20 команд над инфраструктурой. Вариант Б: выделить 3–5 модулей монолита с наибольшей частотой изменений в отдельно релизуемые компоненты (первый шаг к декомпозиции, см. 3.5), перевести их на еженедельный ритм за полгода, остальной монолит оставить на ежемесячном ритме до дальнейшей декомпозиции. Быстрее для самых активных команд, но создаёт два релизных процесса. Выбирайте А, если монолит архитектурно не позволяет выделять модули без большого рефакторинга; Б — если 80% изменений приходится на 20% модулей, что типично. Противникам: ИБ получает автоматический след и меньшие изменения для анализа; эксплуатация — релизы без ночных смен и с откатом за минуты. Их нужно включить в рабочую группу с первого дня, а не убеждать презентацией.
Антипаттерны
Одна техника для всего. «Мы всегда делаем canary» → canary не поймает дефект в редком детерминированном сценарии, blue-green не подходит с миграцией схемы → выбор от вопросов: как проявится дефект, можно ли частично, что с данными.
Поезд, который двигается. Расписание сдвигается «ради важной фичи» → поезд перестаёт быть поездом, каждая фича становится важной → расписание фиксировано, фичи ждут или едут за флагом.
Откат без плана для данных. План отката описывает только код → откат оставляет данные в несовместимом состоянии, пользователи теряют операции → раздел «данные» в каждом плане отката, expand-contract для миграций.
Флаги без гигиены. Флаги добавляются, но не удаляются → сотни флагов, комбинаторные дефекты, никто не знает, что включено → каждый флаг с владельцем и датой удаления, отчёт о флагах старше [N] месяцев.
Триггер отката — «если что-то пойдёт не так». Дежурный принимает решение по ощущению, обычно поздно → метрика, порог, кто решает без согласования, за сколько минут.
Deploy равно release. Кандидат не различает выкатку кода и включение функции → не понимает, как флаги развязывают команды и снимают риск сторов → разделяйте термины явно.
