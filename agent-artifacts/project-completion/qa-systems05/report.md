# Независимая QA пяти самостоятельных ситуаций

Приняты по содержанию 5 из 5. Открытых замечаний к кейсам нет. Хеш cases.json: 349a2c73fabfdbdd111b248aeb9cc57d292c777d5b6e81d9d892bba7e905d37a. Решение об импорте и заморозке не входит в эту приёмку.

**TC-120 · B · head**. §4.3, ART как единица планирования ёмкости и типичный срыв IP. Между двумя поездами требуется связать правила обещаний, изменение KPI и согласованный перенос продуктового объёма. Полномочия и цена решения заданы. A не меняет доступную мощность, C снимает конфликт на квартал, D оставляет весь прежний объём. C выше D и A. В другой ситуации D целиком подходит при уже учтённых в обещаниях инженерных результатах. TC-098 защищает денежный резерв для неизвестных рисков решением спонсора. Здесь работа заранее известна и есть стимул повторно продать время. TC-039 и 111 меняют координацию и права PO.

**TC-143 · D · junior**. §3.3 отделяет deploy от release. Одно явное правило полномочий, в том числе для 1%. C сохраняет полномочия, но добавляет повторное развёртывание. B и A открывают разный охват без решения. Их when описывают конкретное предварительное разрешение владельца, а C требует невозможности безопасно держать сборку. TC-005 управляет сроком магазина при уже обещанной дате. TC-061 оптимизирует охват разрешённого запуска, 133/134 разрешают конфликт за общий ресурс.

**TC-189 · A · junior**. §3.3, гигиена временных флагов. Учащийся применяет правило завершения после явного исключения внешних потребителей и зависимости отката. D задаёт проверку и дату, но препятствия сняты. C экономит регресс, оставляя достижимый непроверенный путь. B сохраняет его и двойной регресс. Отдельные проверки аудитории оправдывают C, отдельная проверяемая резервная конфигурация — B. TC-010/037/054/055 проверяют способность вернуть данные или поведение при запуске. Здесь резерв уже доказан и речь о снятии технического долга после запуска.

**TC-241 · C · junior**. §10.1, балансировщик, stateless-слой, общая база, снижение нагрузки на чтение. Junior указывает измеренный участок ожидания, выбор реализации оставлен архитектору. A и B меняют промежуточный слой при равномерном распределении и запасе CPU. D может ухудшить уже измеренную очередь. При слепом просмотре D казался ближайшим к правильному слою, но близость к базе не даёт частичного устранения причины. Низкий балл D обоснован. В контрфактах явно разделены очереди CPU, балансировки и клиентского пула. TC-110 требует переноса состояния сессий. TC-190/297 выявляют вторичную нагрузку от наполнения кэша. TC-214 уже выбирает конкретный кэш с ограничениями свежести.

**TC-249 · D · junior**. §10.1, таблица REST/gRPC. Клиент JSON, задержка в норме, выигрыш не покрывает вытеснение работы. Для Junior достаточно распознать явное отсутствие требования. A сохраняет контракт и даёт второй реальный вход, C добавляет внутренний перевод без потребности, B требует смены клиента. Их when предполагают соответственно подтверждённого второго потребителя, внутренние сервисы с окупаемым шлюзом или готовность обеих сторон и выгоду переключения. TC-011/038/265 определяют безопасное снятие старого API после миграции. Здесь решается предшествующий вопрос о целесообразности самой инвестиции.

Слепые выборы и вторые варианты сохранены до открытия ключа. Отдельную оценку уверенности до открытия ключа не записывал. Все первые выборы совпали, расхождение по второму выбору TC-241 разобрано выше. Среди пяти правильных ответов три самые длинные по символам, а в TC-189 правильный короче двух альтернатив. Позиции ключа распределены по всем четырём буквам. Внутри пакета разные решения, связанных семей нет. Проверка Swift унаследована только для точного хеша.
